# تأیید و تحویل کار

این قابلیت به هر تسک تاریخچهٔ تحویل می‌دهد. هر نسخه شامل توضیح خروجی، لینک
اختیاری و یک بررسی‌کننده است. بررسی‌کننده نسخه را تأیید می‌کند یا با ذکر دلیل
برای اصلاح برمی‌گرداند. نسخهٔ اصلاح‌شده یک تحویل جدید است؛ متن و نتیجهٔ نسخهٔ
قبلی بازنویسی نمی‌شود.

## قرارداد API

تمام مسیرها زیر این نشانی‌اند و هدرهای احراز هویت معمول API را می‌خواهند:

```text
/projects/{projectID}/tasks/{taskID}/deliveries
```

| متد | مسیر نسبت به نشانی بالا | کاربرد |
| --- | --- | --- |
| POST | نشانی پایه | تحویل نسخهٔ جدید برای بررسی |
| GET | `?limit=20&cursor=…` | تاریخچه؛ جدیدترین نسخه ابتدا |
| GET | `/{deliveryID}` | جزئیات یک نسخه |
| POST | `/{deliveryID}/review` | تأیید یا درخواست اصلاح |
| POST | `/{deliveryID}/withdraw` | پس‌گرفتن تحویلِ منتظر بررسی |

ارسال نسخهٔ جدید، با هویت مسئول تسک:

```http
POST /projects/{projectID}/tasks/{taskID}/deliveries
Content-Type: application/json
X-APIKEY: <token>
USER-ID: alice
APP-ID: <tenant>

{
  "reviewerUserId": "bob",
  "body": "نسخهٔ اصلاح‌شده آماده است؛ معیارهای پذیرش در لینک پیوست بررسی شدند.",
  "outputUrl": "https://example.com/output/v2"
}
```

پاسخ موفق `201` و شامل رکورد زیر است:

```json
{
  "id": "<delivery-uuid>",
  "projectId": "<project-uuid>",
  "taskId": "<task-uuid>",
  "revision": 1,
  "submittedByUserId": "alice",
  "reviewerUserId": "bob",
  "body": "نسخهٔ اصلاح‌شده آماده است؛ معیارهای پذیرش در لینک پیوست بررسی شدند.",
  "outputUrl": "https://example.com/output/v2",
  "status": "pending",
  "submittedAt": "2026-10-21T12:00:00Z",
  "reviewedByUserId": null,
  "reviewNote": null,
  "reviewedAt": null
}
```

برگشت برای اصلاح، با هویت بررسی‌کنندهٔ تعیین‌شده:

```http
POST /projects/{projectID}/tasks/{taskID}/deliveries/{deliveryID}/review
Content-Type: application/json
X-APIKEY: <token>
USER-ID: bob
APP-ID: <tenant>

{"decision":"changes_requested","note":"حالت خطای فرم هنوز پیاده نشده است."}
```

برای تأیید، بدنهٔ `{"decision":"approved","note":"تأیید شد."}` را به همان
مسیر بفرستید. یادداشت تأیید اختیاری است. هر دو عمل `200` و رکورد به‌روز را
برمی‌گردانند. پس از درخواست اصلاح، ارسال‌کننده نسخهٔ جدید را با `POST` روی
فهرست تحویل‌ها ثبت می‌کند؛ شمارهٔ نسخه در سرور افزایش می‌یابد.

پس‌گرفتن تحویلِ هنوز بررسی‌نشده:

```http
POST /projects/{projectID}/tasks/{taskID}/deliveries/{deliveryID}/withdraw
Content-Type: application/json

{"note":"بررسی‌کننده عوض می‌شود؛ نسخهٔ جدید ارسال می‌کنم."}
```

هدرهای هویت ارسال‌کننده یا مدیر پروژه را بفرستید. یادداشت اختیاری است؛ برای
پس‌گرفتن بدون یادداشت، بدنهٔ `{}` لازم است. وضعیت به `withdrawn` تغییر می‌کند
و ارسال نسخهٔ جدید دوباره ممکن می‌شود. رکورد پس‌گرفته‌شده حذف نمی‌شود.

## مجوز و قواعد

- مسئول تسک می‌تواند تحویل بدهد. برای تسک بدون مسئول، ایجادکنندهٔ تسک هم
  می‌تواند تحویل بدهد. مدیر پروژه و مدیر فضای کاری می‌توانند از طرف تیم ارسال کنند.
- بررسی‌کننده باید عضو یا مدیر فعلی همان پروژه باشد. نقش بیننده برای بررسی
  کافی نیست. ارسال‌کننده و مسئول خروجی نمی‌توانند بررسی‌کنندهٔ همان تحویل باشند؛
  حتی اگر مدیر به‌جای مسئول تسک، تحویل را ثبت کند.
- فقط بررسی‌کنندهٔ تعیین‌شده می‌تواند تصمیم ثبت کند؛ مدیرِ دیگری هم نمی‌تواند
  جای او تأیید کند. در صورت خروج بررسی‌کننده از پروژه، ارسال‌کننده یا مدیر
  می‌تواند تحویل را پس بگیرد و نسخهٔ جدیدی برای فرد دیگری بفرستد.
- بیننده تاریخچه را می‌خواند، ولی نمی‌تواند ارسال، بررسی یا پس‌گرفتن انجام دهد.
- فقط یک نسخهٔ `pending` برای هر تسک مجاز است. تصمیم روی نسخهٔ قبلاً بررسی‌شده
  یا پس‌گرفته‌شده قابل تکرار یا تغییر نیست.
- توضیح خروجی ۱ تا ۱۰ هزار نویسه است. یادداشت بررسی حداکثر ۲۰۰۰ نویسه است؛
  برای `changes_requested`، یادداشتِ غیرخالی اجباری است.
- لینک خروجی اختیاری و حداکثر ۲۰۴۸ بایت است؛ فقط HTTP/HTTPS پذیرفته می‌شود.
  سرور لینک را واکشی نمی‌کند. متن و نشانی لینک ذخیره می‌شوند؛ محتوای صفحهٔ
  خارجی یا فایل‌های تسک با این عملیات نسخه‌برداری نمی‌شود.
- پروژه و تسک باید فعال باشند. آرشیو، دسترسی این مسیرها را متوقف می‌کند؛
  بازیابی پروژه/تسک، تاریخچه را دوباره در دسترس می‌گذارد.

`pending` به یکی از `approved`، `changes_requested` یا `withdrawn` تغییر می‌کند.
هر ارسال جدید، یک رکورد `pending` با شمارهٔ نسخهٔ بعدی می‌سازد؛ ارسال مجدد پس از
تأیید هم ممکن است، چون می‌تواند خروجی تازه‌ای برای همان تسک وجود داشته باشد.

وضعیت تحویل از وضعیت برد مستقل است. تأیید خروجی، `statusId` یا `completedAt`
تسک را تغییر نمی‌دهد و این قابلیت، تکمیل دستی تسک را مشروط به تأیید نمی‌کند.

فهرست، `{"items":[…],"nextCursor":"…"}` برمی‌گرداند. `limit` از ۱ تا ۱۰۰
است؛ `nextCursor` را بدون تغییر در درخواست صفحهٔ بعد بفرستید. در آخرین صفحه
مقدار آن `null` است. اولین آیتم، تازه‌ترین نسخه و وضعیت فعلی تحویل است.

خطاهای ورودی `400`، نبود هویت `401`، نداشتن مجوز `403`، نبود منبع یا دسترسی
به منبع خارج از محدوده `404` و تعارض با وضعیت تحویل `409` هستند. وضعیت، شمارهٔ
نسخه، فرستنده و زمان‌ها از سرور می‌آیند؛ ارسال این فیلدها در JSON پذیرفته نمی‌شود.

## مسیر کد و اطمینان از ذخیره‌سازی

1. `internal/task/handler_delivery.go` بدنهٔ HTTP را با ابزار JSON موجود پروژه
   می‌خواند؛ فیلدهای ناشناخته رد می‌شوند.
2. `internal/task/delivery.go` متن، نشانی خروجی، مجوز و قواعد مالکیت را بررسی می‌کند.
3. `internal/task/repository_delivery.go` در یک تراکنش، پروژه و تسک را قفل
   می‌کند، دسترسی جاری را دوباره بررسی می‌کند و تغییر تحویل را ذخیره می‌کند.
4. همان تراکنش یک رویداد در activity ثبت می‌کند. شکست ثبت رویداد، تغییر تحویل
   را هم برمی‌گرداند. قید یکتای دیتابیس از دو تحویل منتظر بررسی جلوگیری می‌کند.
5. پس از commit، ارسال و پس‌گرفتن به بررسی‌کننده و نتیجهٔ بررسی به ارسال‌کننده
   اعلان می‌شود. گیرنده‌ای که دیگر عضو پروژه نیست اعلان نمی‌گیرد.

رویدادهای activity از نوع `task.delivery.submitted`، `task.delivery.approved`،
`task.delivery.changes_requested` و `task.delivery.withdrawn` هستند. متادیتا
شامل شناسهٔ تحویل، نسخه و وضعیت است؛ دلیل بررسی در خود تاریخچهٔ تحویل ذخیره می‌شود.

اعلان‌ها از dispatcher فعلی استفاده می‌کنند؛ ارسال آن‌ها best-effort است و
خرابی سرویس اعلان، ثبت تحویل یا نتیجهٔ بررسی را لغو نمی‌کند. برای مشاهدهٔ قطعی
نتیجه، تاریخچهٔ تحویل منبع اصلی است. این نسخه رویداد جدیدی به موتور اتوماسیون
تسک نمی‌فرستد.

## نصب و آزمون

Migration شمارهٔ ۲۲ را با روند معمول پروژه اعمال کنید و API را بازسازی کنید:

```sh
docker compose run --rm migrate
docker compose up --build -d api
```

برای نصب بدون Docker از دستور migration موجود در README استفاده کنید.

```sh
go test ./internal/task ./internal/project
TASKMANAGER_TEST_DATABASE_URL='postgres://taskmanager:taskmanager@localhost:5432/taskmanager_test?sslmode=disable' go test ./internal/task -run 'Test.*Deliver' -v
```

آزمون‌های دیتابیس، چرخهٔ ارسال/اصلاح/تأیید، نسخه‌بندی، دسترسی‌ها، پس‌گرفتن،
درخواست‌های هم‌زمان و rollback در شکست ثبت activity را در schema موقت بررسی
می‌کنند. بدون `TASKMANAGER_TEST_DATABASE_URL` این آزمون‌ها skip می‌شوند.
پایگاه دادهٔ آزمون باید از قبل وجود داشته باشد؛ از دیتابیس عملیاتی استفاده نکنید.
