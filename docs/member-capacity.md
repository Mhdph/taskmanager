# مدیریت ظرفیت اعضا

ظرفیت نشان می‌دهد هر عضو در چه روزهایی و روزانه چند ساعت برای کار وقت دارد.
گزارش بار کار، زمان باقی‌ماندهٔ تسک‌های باز را با این ظرفیت مقایسه می‌کند.
واحد همهٔ مدت‌ها ثانیه است؛ درصد استفاده از ظرفیت می‌تواند بیشتر از ۱۰۰ باشد.

## تنظیم ظرفیت

فقط مدیر فضای کاری، نقش‌های دایرکتوری `owner`/`admin` و هویت‌های hosted
admin/support می‌توانند ظرفیت را تعیین یا پاک کنند. عضو عادی فقط ظرفیت خودش
را می‌خواند. همهٔ اطلاعات به tenant هویت احراز‌شده محدود است.

```http
PUT /members/{userID}/capacity
Content-Type: application/json
X-APIKEY: <token>
USER-ID: <workspace-manager>
APP-ID: <tenant>

{
  "dailyCapacitySeconds": 28800,
  "workingDays": [6, 7, 1, 2, 3],
  "timezone": "Asia/Tehran"
}
```

این نمونه ۸ ساعت در روز، از شنبه تا چهارشنبه است. روزها ISO هستند:
۱ دوشنبه، ۲ سه‌شنبه، ۳ چهارشنبه، ۴ پنجشنبه، ۵ جمعه، ۶ شنبه و ۷ یکشنبه.
هر سه فیلد الزامی‌اند. ساعت روزانه از صفر تا ۸۶۴۰۰ ثانیه است؛ روزهای تکراری
پذیرفته نمی‌شوند و timezone باید یک نام معتبر IANA یا `UTC` باشد.

`PUT` کل تنظیم را جایگزین می‌کند و `200` برمی‌گرداند:

```json
{
  "userId": "alice",
  "configured": true,
  "dailyCapacitySeconds": 28800,
  "workingDays": [1, 2, 3, 6, 7],
  "timezone": "Asia/Tehran"
}
```

- `GET /members/{userID}/capacity`: خواندن تنظیم فعلی توسط خود فرد یا مدیر.
- `DELETE /members/{userID}/capacity`: پاک‌کردن تنظیم توسط مدیر؛ پاسخ `204`.
- ظرفیت تنظیم‌نشده با `configured:false` و فیلدهای `null` برمی‌گردد؛ پیش‌فرض
  پنهانِ ۸ ساعت یا هفتهٔ کاری خاصی وجود ندارد.
- ظرفیت صفر یا `workingDays:[]` یعنی زمان در دسترس صفر است؛ با «تنظیم نشده»
  متفاوت است. می‌توان از آن برای مشخص‌کردن عدم دسترسی استفاده کرد، ولی این
  نسخه تقویم مرخصی یا ظرفیت متفاوت برای تاریخ‌های مشخص ندارد.

## گزارش ظرفیت و بار کار

گزارش کل اعضا فقط برای مدیر فضای کاری:

```http
GET /workload?from=2026-10-24&to=2026-10-30&limit=50
```

گزارش یک عضو برای خود او یا مدیر:

```http
GET /members/{userID}/workload?from=2026-10-24&to=2026-10-30
```

`from` و `to` تاریخ میلادی `YYYY-MM-DD` و هر دو شامل بازه هستند؛ حداکثر بازه
۹۲ روز است. `limit` از ۱ تا ۲۰۰ و پیش‌فرض ۵۰ است. گزارش سراسری براساس اعضا
صفحه‌بندی می‌شود؛ مقدار `nextCursor` را بدون تغییر و با URL encoding به
`cursor` بدهید. گزارش تک‌عضو cursor نمی‌گیرد.

روزهای گزارش در منطقهٔ زمانی تنظیم‌شدهٔ هر عضو محاسبه می‌شوند. برای اعضای
بدون تنظیم، `timezone` درخواست استفاده می‌شود؛ پیش‌فرض آن `Asia/Tehran` است.
این پارامتر منطقهٔ زمانی پروفایلِ تنظیم‌شده را عوض نمی‌کند.

شکل پاسخ:

```json
{
  "from": "2026-10-24",
  "to": "2026-10-30",
  "scope": "workspace",
  "items": [
    {
      "userId": "alice",
      "firstName": "نام",
      "lastName": "عضو",
      "capacity": {"userId":"alice","configured":true,"dailyCapacitySeconds":28800,"workingDays":[1,2,3,6,7],"timezone":"Asia/Tehran"},
      "timezone": "Asia/Tehran",
      "days": [
        {"date":"2026-10-24","capacitySeconds":28800,"plannedSeconds":36000,"availableSeconds":0,"overloadSeconds":7200,"utilizationPercent":125,"taskCount":2}
      ],
      "totals": {"capacitySeconds":144000,"plannedSeconds":36000,"availableSeconds":115200,"overloadSeconds":7200,"utilizationPercent":25},
      "openTaskCount": 4,
      "unestimatedTaskCount": 1,
      "unscheduledTaskCount": 1,
      "unscheduledSeconds": 14400,
      "overdueTaskCount": 1,
      "overdueSeconds": 7200
    }
  ],
  "nextCursor": null
}
```

در نمونه فقط یک روز نشان داده شده؛ پاسخ واقعی همهٔ روزهای بازه را برمی‌گرداند.
`scope:workspace` یعنی همهٔ پروژه‌های فعال tenant بررسی شده‌اند. گزارش شخصی
عضو عادی `scope:visible_projects` دارد و فقط پروژه‌هایی را می‌شمارد که هنوز
عضو آن‌هاست. اطلاعات پروژه‌های غیرقابل‌دسترسی در جمع بار کار او هم افشا نمی‌شود.
گزارش فقط اعضای فعال را شامل می‌شود؛ اعضای دعوت‌شده وارد محاسبه نمی‌شوند.

## روش محاسبه

1. فقط تسک‌های باز، تخصیص‌یافته و متعلق به پروژه‌های فعال حساب می‌شوند.
   تسک آرشیوشده، `completedAt`دار یا با وضعیت دستهٔ `done` کنار گذاشته می‌شود.
2. زمان باقی‌مانده = حداکثرِ صفر و «برآورد منهای زمان ثبت‌شدهٔ حذف‌نشده».
   زمان‌سنج فعال تا لحظهٔ خواندن گزارش هم حساب می‌شود. زمان‌های ثبت‌شدهٔ همهٔ
   افراد روی تسک از برآورد همان تسک کم می‌شود، حتی اگر مسئولش عوض شده باشد.
3. تسکی که شروع و موعد دارد، زمان باقی‌مانده‌اش را بین روزهای کاری کل آن
   فاصله، با احتساب دو سر، تقسیم می‌کند. سپس سهم روزهای داخل گزارش برداشته
   می‌شود؛ کل برآورد در هر گزارش هفتگی دوباره شمرده نمی‌شود. باقی‌ماندهٔ تقسیم
   ثانیه‌ها به روزهای اول می‌رود تا جمع زمان از بین نرود.
4. تسک فقط دارای موعد روی همان روز، و تسک فقط دارای شروع روی روز شروع قرار
   می‌گیرد. اگر کل فاصله هیچ روز کاری نداشته باشد، بار بین روزهای تقویمی آن
   فاصله قرار می‌گیرد تا کارِ روز تعطیل به‌جای حذف‌شدن، اضافه‌بار نشان داده شود.
5. برای ظرفیت تنظیم‌نشده، توزیع بر روزهای تقویمی است و همهٔ سنجه‌های ظرفیت،
   زمان خالی، اضافه‌بار و درصد `null` هستند؛ فقط بار برآوردشده نمایش داده می‌شود.
6. تسک‌های بدون تاریخ، و تسک‌های فقط دارای شروع پیش از بازه بدون موعد، در
   `unscheduled*` می‌آیند. تسک‌های ناتمام با موعد پیش از بازه در `overdue*`
   هستند. این دو گروه به‌طور خودکار به روز اول گزارش منتقل نمی‌شوند.
7. تسک بدون برآورد در `unestimatedTaskCount` مشخص است و زمان فرضی برایش
   ساخته نمی‌شود. تسک‌هایی که شروعشان، یا در نبود شروع موعدشان، پس از پایان
   گزارش است در آمار این گزارش وارد نمی‌شوند.

`availableSeconds` و `overloadSeconds` جمع مقدارهای روزانه‌اند. بنابراین یک
عضو می‌تواند هم روزهای خالی داشته باشد و هم در روز دیگری اضافه‌بار؛ بار زیاد
شنبه با ظرفیت خالی یکشنبه پنهان نمی‌شود. درصد کلی، جمع بار برنامه‌ریزی‌شده
تقسیم بر جمع ظرفیت است. برای ظرفیت صفر، درصد `null` است و اضافه‌بار همچنان
عددی باقی می‌ماند.

ظرفیت خالی فقط نسبت به کارهای برآوردشده و زمان‌بندی‌شدهٔ داخل بازه است؛ پیش از
تخصیص بیشتر، `unestimated*`، `unscheduled*` و `overdue*` را هم بررسی کنید.
هر تسک و زیرکارِ دارای برآورد، مستقل حساب می‌شود؛ هیچ جمع خودکاری از زیرکارها
به برآورد والد انجام نمی‌شود. برآورد والد را به‌عنوان جمع تکراری همان زیرکارها
وارد نکنید.

این گزارش بر وضعیت فعلی کارها، برآورد باقی‌مانده و آخرین تنظیم ظرفیت بنا شده
است؛ گزارش تاریخیِ ظرفیت یا ثبت تغییرات برنامه در گذشته نیست. خواندن داده‌ها
در یک snapshot دیتابیس انجام می‌شود تا تغییر هم‌زمان ظرفیت و تسک، پاسخ را
ناسازگار نکند. این نسخه به‌صورت خودکار تسک‌ها را جابه‌جا یا به فرد دیگری واگذار
نمی‌کند؛ گزارش ابزار تصمیم‌گیری برای تخصیص و زمان‌بندی است.

## نصب، کد و آزمون

Migration شمارهٔ ۲۴ جدول ظرفیت را می‌سازد. تنظیم‌ها با حذف عضو از tenant حذف
می‌شوند و با sync مشخصات یا ورود مجدد بازنویسی نمی‌شوند.

- `internal/member/capacity.go`: ورودی، خروجی و مجوزها.
- `internal/member/workload.go`: تقسیم زمان بین روزها و سنجه‌های ظرفیت.
- `internal/member/repository_capacity.go`: snapshot گزارش و ذخیرهٔ تنظیم‌ها.
- `internal/member/handler_capacity.go`: APIهای HTTP.
- `db/queries/capacity.sql`: خواندن ظرفیت و بار کار با محدودیت tenant و دسترسی.

```sh
docker compose run --rm migrate
docker compose up --build -d api
go test ./internal/member
TASKMANAGER_TEST_DATABASE_URL='postgres://taskmanager:taskmanager@localhost:5432/taskmanager_test?sslmode=disable' go test ./internal/member -run 'TestMemberCapacity|TestWorkloadEstimates' -v
```

آزمون‌های دیتابیس در schema موقت اجرا می‌شوند؛ بدون متغیر اتصال skip می‌شوند.
آزمون‌های مستقل، تقسیم بین چند هفته، ثانیه‌های باقی‌مانده، بازهٔ جزئی، اضافه‌بار
روز تعطیل، ظرفیت صفر/نامشخص و تغییر ساعت تابستانی را پوشش می‌دهند.
